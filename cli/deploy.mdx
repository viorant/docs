---
title: "Deploy an agent"
description: "Put a .vio agent on Viorant Cloud from your terminal, on Viorant credits or your own provider key, and call it."
---

Deploying gives the agent its own URL on Viorant Cloud. It keeps running whether your
terminal — or the Hub — is open or not.

<Note>
  Needs `vio` **1.0.0** or later for credits deploys and the `vio connect` behaviour
  described here. Check with `vio --version`.
</Note>

## Before you deploy

- [Sign in](/cli/sign-in) with `vio login`.
- Make sure `vio validate agent.vio` passes. A stale digest is refused at deploy —
  see [Validate a .vio file](/cli/validate).
- Check you have room: `vio status` shows how many agents your plan still allows.
- Decide how the agent pays for its model: **Viorant credits**, or **your own provider
  key**.

## Credits or your own key

The bundle decides, through its agent's model reference.

### Viorant credits

An agent whose model is one of Viorant's managed models runs on your wallet. There is no
provider key to find, store or send:

```yaml title="agent.vio (the agent artifact)"
model:
  ref: provider://openai-compatible/viorant-managed-mid
```

Three tiers, all under `provider://openai-compatible/`:

| Tier | For | Plan |
| --- | --- | --- |
| `viorant-managed-low` | fastest and cheapest — routine tasks | every plan |
| `viorant-managed-mid` | balanced; the recommended default | every plan |
| `viorant-managed-high` | most capable — complex or high-stakes tasks | **Pro** only |

`vio providers` prints this same list, with Viorant credits shown first. A bundle deploys on
credits only when **every** agent in it uses one of these tiers; anything else — including a
mix — is treated as your own key.

<Warning>
  A `high` agent **deploys fine on Free or Starter** — the tier is not checked at deploy
  time. But **every run then fails** with `plans.tier_not_allowed`, because the plan is
  checked per run, not at deploy. Use `low` or `mid` unless the account is on Pro — check
  with `vio status`.
</Warning>

Changing the model changes the agent's body, so run `vio digest agent.vio --fix` after
the edit.

Before a credits deploy, `vio` prints one line:

```
Runs on this agent spend credits from your wallet.
```

The deploy itself spends nothing. Each run of the deployed agent does. `vio status` shows
your balance. A credits agent runs on Viorant Cloud only.

### Your own key (BYOK)

Any other model — `provider://openai/gpt-4o-mini`, `provider://gemini/…` and so on — runs
on your own provider key, which `vio` seals on your machine and delivers straight to the
deployment.

Inside a [Space](/cli/init), `vio init` creates `.vio/.env.provider`, you fill it in, and
`vio deploy` reads it. `.vio/` is git-ignored, so the key never reaches a commit.

```bash title=".vio/.env.provider"
VIORANT_RUNNER_PROVIDER_KIND=gemini
VIORANT_RUNNER_PROVIDER_MODEL=gemini-2.5-flash
GOOGLE_GENERATIVE_AI_API_KEY=...
```

`VIORANT_RUNNER_PROVIDER_KIND` must match the bundle's model: a `provider://gemini/…`
agent needs `gemini`. If they differ, `vio` refuses before anything is sent, names both,
and says `Nothing was deployed.` — otherwise the agent would wait forever for a key it
never gets. `vio providers` lists every kind and the key variable it needs.

Outside a Space — a loose `.vio` someone sent you — pass a file explicitly with
`--env-file`, kept outside the repository and never committed. An `--env-file` always wins
over the Space's own credentials.

<Note>
  Credentials are read from the Space that holds **the bundle you are deploying**, not
  from the folder you happen to be standing in. `vio deploy ../other-agent/agent.vio`
  uses `../other-agent`'s key, not this one's.
</Note>

## Deploy

From the [shell](/cli/shell):

```
> /deploy agent.vio --target viorant_cloud
```

Or as a subcommand, which is what scripts, CI and AI agents use:

```bash
vio deploy agent.vio --target viorant_cloud
```

`vio` validates the file on your machine — the same checks as `vio validate` — then asks
Viorant Cloud to stand the agent up.

- `--env-file <file>` names the credentials file (both forms).
- `--name "My agent"` sets the deployment name; it defaults to the name in the file.
- `--json` prints one JSON object, for scripts.

`--name` and `--json` are subcommand-only.

<Warning>
  Deploying creates an internet-reachable service that counts against your plan's agent
  limit, and — for a BYOK agent — sends your provider key to it. `vio` itself never
  prompts — if a coding agent runs it for you, whether it asks first is your agent's
  permission setting, not `vio`'s. See [Use `vio` with AI coding agents](/cli/ai-agents).
</Warning>

## Call the agent

On success, `vio` prints the deployment id, its URL and a **run key**. The run key is shown
**once** — `vio` never writes it to disk. Store it somewhere safe.

```bash
curl -sS -X POST https://<service>.a.run.app/run \
  -H "Authorization: Bearer <run key>" \
  -H "Content-Type: application/json" \
  -d '{"task":"..."}'
```

`vio` also prints an example request body built from the inputs your agent declares.

To run it on a timer instead, see [Schedule an agent](/cli/schedule).
